# 일반 회원 예약 HTTP 429 처리 — 2026-11-10

## 확인한 소스와 미확인 원인

사진의 `Server responded with status 429`는 설치된 Firebase Firestore SDK 9.6.1의 REST RPC 오류 문구와 일치한다. 구조화된 Firebase 오류 본문이 없는 HTTP 429는 SDK에서 `unknown` 오류로 변환된다. 기존 `saveBook`은 이를 재시도하지 않고 오류 문구를 그대로 표시했다. 일반 회원은 관리자와 달리 저장 후 `maybeAutoBlockUser`를 호출하며, 이 보조 처리의 오류가 이미 성공한 예약까지 실패로 표시할 수 있었다.

운영 Firebase 요청·사용량 조회·실제 예약 재현은 하지 않았다. 따라서 운영에서 429가 발생한 RPC와 원인(순간 요청 제한, 서버/네트워크 제한, 할당량 등)은 확정하지 않았다. 지속적인 할당량 부족은 이 클라이언트 수정만으로 해소되지 않는다.

## 이번 변경

- 예약 트랜잭션의 429는 약 1초·2.5초(작은 무작위 지연 포함) 후 최대 2회만 재시도한다. 명시적인 daily/quota 오류와 권한·충돌 오류는 자동 재시도하지 않는다.
- 재시도는 같은 requestId·회원 UID·결제 식별자·구장·날짜·슬롯을 유지한다. 매번 모든 슬롯을 먼저 읽고 기존 원자적 충돌 검사와 저장 필드를 유지한다. 서버에 이미 저장된 바로 그 요청의 모든 슬롯만 성공으로 인정하며 다른 요청/부분 충돌은 덮어쓰지 않는다.
- 회원의 신청 처리 중 버튼과 중복 함수 호출을 잠그고 계좌이체 저장을 기다린다. 완료/실패 시 잠금을 해제하며 요금·동의·본인 확인 조건은 계속 적용한다.
- 저장 후 모니터링 실패는 이미 저장된 예약을 실패로 표시하지 않는다. 재시도 소진 시에는 잠시 후 내 예약에서 신청 여부를 확인하도록 안내한다. 무조건 성공 처리하거나 충돌/사용량 제한을 우회하지 않는다.
- 요금·환불·일일 예약 제한·PG 요청 본문·계좌이체 PENDING/관리자 BOOKED 저장 형식은 유지한다. 기존 PG 서버 검증·환불/결제 보상 구조는 이번 범위에 포함하지 않는다.

## 재현 및 검증 방법

`node --test tests/*.test.mjs`는 저장 전 429, 저장 후 응답 유실, 다른 요청의 슬롯 충돌, 영구 429, 권한/할당량 오류, 중복 클릭, 구장 변경, 저장 후 모니터링 오류 및 관리자 저장을 검증한다. 기존 미수정 TODO는 통과 테스트와 구분한다.

`npm.cmd run test:booking-rate-limit`는 demo Emulator와 로컬 workerd에서 실제 SDK RPC에 HTTP 429를 주입한다. 첫 batchGet은 429를 반환하고, 첫 commit은 Emulator 저장 성공 후 응답만 429로 바꾼다. 두 슬롯이 PENDING/TRANSFER로 한 번만 저장되고 카드 호출이 없는지 확인한다. 저장 후 모니터링 오류도 주입한다. 운영 API·결제·발송은 사용하지 않는다. Java/Storage의 느린 초기 시작을 위해 Emulator 시작 대기만 최대 3분으로 늘렸다.

같은 검증 환경에서 Windows `Path`를 `PATH`로만 읽어 Git 경로가 유실되는 도구 문제도 수정했다. 이 변경은 로컬 빌드/검증 하위 프로세스의 도구 경로와 자격 증명 제거에만 적용하며 앱의 Firebase 설정을 바꾸지 않는다. `tests/local-tool-path.test.mjs`로 Windows/Linux 표기를 모두 검증한다.

배포 후 확인은 정적 자원 비교와 JavaScript 비활성 화면으로 제한한다. 실제 일반 회원의 예약 성공 여부를 운영에서 대신 시험하지 않는다.
