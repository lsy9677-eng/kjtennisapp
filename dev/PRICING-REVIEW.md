# 기존 요금 설정과 계산 경로 조사

사용자 기준: 현재 평일·주말 금액은 같고, 계절 설정은 라이트 사용에 따른 야간 시작 시각 조정이 주목적이다. 향후 금액은 달라질 수 있다. 운영 사이트·Firebase·결제 내역에 접근하지 않았다. 아래 운영 기준은 사용자 설명이며 DB 값 확인 결과가 아니다. 최초 조사는 소스와 가상 메모리 설정만 사용했다. 이후 요청으로 아래 두 항목만 수정했다.

## 이번 수정과 현재 검증

1. 주말 판정의 불필요한 async를 제거해 공용 요금표와 상세 설명이 같은 평일/주말 값을 사용한다. 기존 요금표의 값은 바꾸지 않았다.
2. 예약창은 기본 설정과 서버 계절 설정을 기다린 뒤 계산하고 결제 가능 상태로 바꾼다. 읽기 실패·잘못된 요금표·변경된 예약 선택은 금액을 확정하지 않으며 버튼과 직접 결제 호출도 차단한다. 실패하면 예약창을 다시 열어 재시도할 수 있다. 정상 빈 시즌은 기본 시작 시각을 사용한다.

`booking-price-readiness.test.mjs` 8개와 기존 요금/시즌 검사로 동일/상이 요금·야간 정각·기간 경계·지연·실패·재시도를 확인한다. 아래 계산 경로와 표는 **수정 전 조사 기록**이다. 현재는 가상 월요일 1000/3000원, 토요일 5000/7000원이며 요금 설명도 일치한다. 더치페이·환불 함수, 시즌 금액 선택 로직, 예약 저장 트랜잭션과 PG 요청 본문은 원본 보존 검사로 확인한다. 공용 날짜 판정의 수정은 해당 공용 요금표를 쓰는 경로에도 적용된다.

최종 단위 검사는 34개 통과, 범위 밖 TODO 5개다. demo Emulator와 실제 로컬 workerd 브라우저에서도 가상 로드 지연·실패 중 버튼 비활성화/직접 결제 호출 차단, 성공 후 야간 설명과 예약 저장을 확인했다. 외부 요청은 0건이다. 실제 운영 배포·데이터·실제 결제는 검증하거나 변경하지 않았다.

커밋 전 최종 검토에서 초기 loadConfig 실패의 미처리 Promise를 최초 호출부에서 처리하도록 보완했다. 운영 URL 문자열을 쓰는 전체 HTML 초기화 검사는 모든 네트워크 요청을 메모리에서 충족하며 Firebase 경계도 가상 대역이다. 초기 실패 후 재시도, 기본/계절 설정 읽기 실패 후 복구, 동의/reCAPTCHA 이후 버튼 복구를 확인했고 데이터 쓰기·결제 호출은 0건이다. 별도 실제 Firebase SDK 메모리 검사는 기존 가상 세션 복원을 확인한다. 배포된 운영 초기화를 확인한 것은 아니다.

## 이미 존재하는 설정

| 관리자/저장 경로 | 실제 계산 연결 |
| --- | --- |
| `openConf()`의 평일주간·평일야간·주말주간·주말야간 입력 | `saveSet()`이 각 값을 시민/비시민 2칸에 복제해 `settings/global.prices` 8개 값 저장. `applyGlobalConfigDoc()`이 4×2 행렬로 복원 |
| `settings/global.nightStartHour` | 시즌이 없으면 기본 야간 시작에 사용, 누락 시 19시 |
| 기존 계절별 요금 설정 UI | `saveSeasonalPricing()`이 start/end/nightStart/dayPrice/nightPrice를 `settings/seasonalPricing.list`에 저장. `loadSeasonalPricings()`로 읽음 |
| 기간별 `nightStart` | 해당 예약일에 일치하는 시즌이면 기본 시각 대신 사용. `time >= nightStart`부터 야간 행 적용 |
| 기본/기간별 `dayPrice`, `nightPrice` | `getPriceForDate()` 및 더치페이 `getReservationPrice()`에 사용. 결제 단가 행렬을 덮어쓰지는 않음 |

기본 시간/단일 금액을 저장하는 `savePriceSettings()` 함수도 있으나, 현재 HTML에는 `settingDayStart/settingNightStart/settingDayPrice/settingNightPrice` 입력이나 이 함수 호출 버튼이 없다. 현재 접근 가능한 UI는 기존 4행 요금표와 기간별 설정이다. 새 설정 기능을 추가할 필요가 있다는 결론은 내리지 않았다.

## 수정 전 계산 호출과 문제

- 예약 모달: `openBook → calcPay → getMatrixPriceBySlot → getConfiguredPriceInfo`. 단가는 `prices` 행렬, 야간 여부는 기본/시즌 시작 시각으로 결정한다.
- 결제 요청: `doPay`가 화면 `txtPrice`를 읽는다. 이 조사에서는 호출하거나 결제하지 않았다.
- 환불 예정액: `calcRefund → getMatrixPriceBySlot`. 통계: customPrice가 없으면 `calcPrice → getMatrixPriceBySlot`.
- 더치페이: `getReservationPrice → getPriceForDate`의 단일/계절 금액을 사용하므로 별도 경로다.

`isWeekendOrHoliday()`가 async인데 calcPay와 getMatrixPriceBySlot은 await 없이 사용한다. 그 결과 평일에도 주말 행과 주말 설명이 선택된다. **동일 금액인 현재 기준에서는 이 행 선택 문제만으로 금액 차이를 입증할 수 없다.** 설명의 주말 표시는 별도 표시 문제다.

소스의 초기 `prices` 기본값은 평일·주말이 서로 다르며, 운영 요금표를 뜻하지 않는다. 저장된 global 설정을 읽으면 그 값으로 교체된다. 따라서 동일 요금이라는 결론은 사용자 기준에 맞는 설정이 로드된 경우에 한하며, 초기 기본값 사용 여부나 실제 운영 설정 로드 실패는 확인하지 않았다.

## 수정 전: 기존 관리자 입력 형태의 가상 금액 결과

아래 금액은 실제 요금이 아니다. 시민/비시민 두 열은 관리자 저장 방식대로 같은 값으로 두었다.

| 가상 설정/예약 | 구분에 맞는 금액 | 기존 코드 결과 |
| --- | --- | --- |
| 평일·주말 모두 주간 1000 / 야간 3000 | 월·토 모두 1000 / 3000 | 동일하게 1000 / 3000. 월요일 설명은 주말로 표시 |
| 평일 주간 1000 / 야간 3000, 주말 주간 5000 / 야간 7000 — 월요일 | 1000 / 3000 | 5000 / 7000: 향후 상이 설정에서 드러나는 결함 |
| 위 상이 설정 — 토요일 | 5000 / 7000 | 5000 / 7000 |
| 기본 19시, 해당 시즌 18시, 공통 주간 1000 / 야간 3000 | 17시 1000, 18시부터 3000 | 동일. 계절별 라이트 시작 시각 연결 확인 |

계절의 별도 가상 금액 111/222를 넣으면 결제는 행렬 1000/3000, 더치페이는 111/222를 사용한다. 현재 설정값이 서로 같은지는 읽지 않았다. 이 사실을 계절 금액을 결제에 새로 적용하라는 요구나 현재 과금 오류로 해석하지 않는다.

## 자정·시즌 경계

- 정규 `YYYY-MM-DD` 예약일 문자열을 비교한다. 시작일과 종료일 모두 포함한다. 11월 30일 종료, 12월 1일 시작처럼 인접하되 겹치지 않으면 각각 올바른 시즌이 적용된다.
- `2026-12-01 ~ 2027-02-28`처럼 연도를 명시한 겨울 기간은 연말을 넘어 적용된다. 매년 자동 반복되는 규칙은 아니다.
- 해당 시즌이 없는 날짜는 기본 nightStartHour로 돌아간다. 선택한 예약일 기준이며 현재 시각이 자정을 지났다는 이유만으로 다른 시즌으로 바꾸지 않는다.
- 야간 시작 정각은 포함한다. 18시 설정이면 17시는 주간, 18시부터 야간이다.
- 0시는 선택 날짜의 시작으로 처리한다. 전날 23시가 야간이어도 다음 날 0시는 일반적인 18/19시 시작 규칙에서 주간이다. `nightStart=0`이면 그 날짜의 모든 시간이 야간이다. 전날 야간을 다음 날 아침까지 연장하는 모델은 없다.
- 현재 예약 그리드는 06~21시 시작 슬롯(22시 종료)이므로 자정 예약 자체는 UI에서 제공하지 않는다. 24시 입력의 다음 날 이월을 지원한다고 볼 근거도 없다.
- 겹치는 시즌은 배열의 첫 항목 우선이다. 같은 경계일을 양쪽 기간에 넣으면 그 날짜가 겹친다. 저장 함수는 날짜 존재만 확인하며 기간 역전·중복·야간 시각 범위를 JS에서 검증하지 않는다. 역전 기간은 일치하지 않고 기본값으로 돌아간다. HTML 숫자 입력 min/max는 0~23이다.
- 수정 전에는 시즌 읽기 완료 전에 기본 19시를 쓸 수 있었다. 현재 기본 설정 로더 자체의 비동기 구조는 유지하되 예약창이 시즌 읽기를 명시적으로 기다리고, 성공 후 계산한다. 실패하면 결제 금액으로 기본값을 사용하지 않는다. 기존 더치페이 로드는 변경하지 않았다.

따라서 정상 비중첩 기간의 날짜/야간 시작 경계는 검사 통과지만, 모든 입력·초기 로드·앱 전체 시간대 처리가 안전하다고 단정하지 않는다.

## 검사 범위

`node --test tests/pricing-settings.test.mjs`: 가상 검사 10개. 관리자 저장은 메모리 대역으로만 포착했고 실제 DB 쓰기는 없다. 원본 함수와 계산 결과를 유지하는 재현 검사이며 결함 해결 검사와 구분한다. 운영 설정·실제 납부액·브라우저 전체 동작·외국 시간대의 날짜 선택은 미검증이다.
